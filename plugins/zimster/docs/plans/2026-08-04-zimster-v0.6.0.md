# Zimster 0.6.0 Adaptive Delegation and Public-Beta Plan

Status: approved for implementation on `feat/adaptive-delegation-v0.6.0`.

Risk: High. Zimster 0.5.0 remains the governing workflow for this self-hosting run. Candidate 0.6.0 behavior may govern only isolated fixtures until its review and acceptance evidence passes.

## Mission

Add task-specific model choice only after Zimster independently decides that bounded delegation materially improves a task. Model availability, price, mappings, and routing policy must never increase delegation frequency. Add bounded autonomous convergence for ordinary deterministic in-scope corrections, and prepare all supported packages and harness surfaces for a truthfully reported public beta.

## Invariants and non-goals

- One persistent logical implementation owner retains final acceptance.
- Delegation has depth one, a bounded role, explicit ownership and tools, a dependency cone, a stop condition, and an owner-run acceptance proof.
- Subagents never recruit subagents. This release adds no delegation trigger, implementation-agent requirement, reviewer lottery, or correction loop.
- Model selection runs only after `delegation.selected=true`; a non-selected decision has no proposal or dispatch.
- Canonical files contain no vendor-model defaults. Local empirical evidence cannot mutate mappings or policy.
- Independent review remains risk-driven and semantic completion remains final.
- No remote routing service, telemetry, prompt upload, secret storage, runtime dependency, or stable 1.0 compatibility claim.

## Canonical flow and artifacts

```text
task assessment
  -> delegation decision
     -> selected=false: persistent owner executes inline; routing stops
     -> selected=true: advisory plan proposal
        -> authoritative dispatch proposal
        -> mapping/config/capability resolution
        -> dispatch and requested/effective accounting
        -> persistent-owner acceptance
```

Add strict JSON schemas and templates for delegation decisions, model proposals, Zimster configuration, routing observations, convergence decisions, and dispatch v2. Dispatch v2 retains top-level requested/effective fields and accepts v1 through a versioned schema branch. Legacy tiers normalize on read: `fast` to `economy`, `standard` to `balanced`, and `expert` to `expert`; absent v2 fields report `legacy_unavailable`.

Plan proposals are permanently advisory. Dispatch proposals are authoritative, single-use, and session-bound. A change to delegation, task signature, Git fingerprint, configuration or mapping digest, harness/version, capability/catalog evidence, or explicit override invalidates them. Regeneration names the superseded proposal.

## Configuration and resolution

Configuration is dependency-free JSON. Highest precedence wins:

1. Explicit dispatch-time user override.
2. Per-run `--config`, snapshotted into Git-local state.
3. `git rev-parse --git-path zimster/config.json`.
4. Native user configuration: XDG/Linux, `~/Library/Application Support/Zimster`/macOS, or `%APPDATA%\\Zimster`/Windows.
5. Harness-native role/session/default configuration.
6. Parent inheritance.

Shipped routing configuration defines only classes, role defaults, legacy aliases, deterministic algorithms, and safe fallbacks. User/project/run mappings declare candidates and optional provider, effort, ranks, harness constraints, and availability source; ties preserve declaration order.

- `recommend`: report a concrete recommendation when evidence permits, but inherit at dispatch absent explicit override.
- `map_only`: use the first available explicit mapping and infer nothing else.
- `auto_within_policy`: choose only mapped and available candidates using policy ranks.
- `inherit`: request neither model nor effort.
- `quality_first`: proposed class or one higher, never lower.
- `balanced`: proposed class or one higher.
- `cost_optimized`: proposed class only, then inherit.

`strict_cost` is valid only with `cost_optimized`. If enforcement or effective-model reporting is unavailable, cancel optional delegation; block required independent review and request one policy exception; never silently inherit a potentially expensive parent. Escalation is deterministic, pre-spawn, and limited to one class. Owner rejection returns work inline.

Comparable empirical summaries require at least three exact categorical matches across harness/version family, role, risk, class, task traits, and proof kind. They may inform an owner but cannot reorder mappings or select or configure a model.

## Harness boundaries

- Codex: explicit per-spawn model/effort, then generated role config, then inherit. Catalog evidence is version/session scoped. Active user config is never edited.
- Claude Code: plugin agents default to portable inheritance. Explicitly generated project/user role overrides outrank plugin definitions and carry ownership manifests.
- Cursor: inherit by default; generate optional compatible agent files only when capability evidence supports the model field.
- Kimi Code: map only symbolic `primary`, verified experimental `secondary`, or inherit.
- OpenCode: optional `provider/model-id` agent config; omission inherits. Prefer current permission fields.
- Pi: owner-inline because Zimster ships no subagent runtime. External extensions are neither installed nor trusted.

Adapters report `native`, `supported_with_constraints`, `prompt_constrained`, `inline_fallback`, `unavailable`, or `unverified`; unsupported routing is never a silent success.

## Autonomous convergence

Move defaults to `config/convergence.json`: two correction commits, two scoped correction rechecks, one reserved exact-final-head review plus one additional review after a final-review correction, two final verification attempts, three complete suites, two exact duplicate commands, and two context renewals. Preserve `final_correction_waves`, `review_rechecks_per_seam`, and `context_compactions` as read aliases.

Continue only when the failure is within the accepted requirement and dependency cone, local, reversible, ordinary, covered by budget, and not caused by missing independent review. Contradictions, material scope expansion, sensitive decisions without authority, policy-required approval, missing review, and exhaustion escalate. Harness and OS permission prompts remain authoritative.

## Acceptance, failure, and rollback

Behavioral evidence covers delegation false despite cheap mappings, required selected-decision fields, advisory/stale/superseded/consumed proposals, every mode/policy/layer/OS path, missing and stale catalogs, unsupported effort, effective mismatch, strict-cost paths, owner rejection, empirical thresholds without mutation, v1 records, every convergence boundary, all allowed escalation reasons, safe generated-file lifecycle, six adapter fallbacks, exact archives, Claude byte budget, and mechanically valid docs.

Final public-beta acceptance requires the exact-tree requirement/evidence matrix, focused and affected tests per slice, release/check/version/sync/doctor/checksum/diff verification, available CI, claim-scoped receipts for all six harnesses, at least one exact-package `LIVE_VERIFIED` host, exact-final-head independent approval, and complete staged/unstaged/committed/untracked inspection. Missing optional host environments narrow their claims; a missing live floor, broad unsupported claim, or missing review blocks `CANDIDATE_COMPLETE`.

Rollback uses revert commits, restores `routing.mode=inherit` and disables autonomous convergence first, removes only owned generated overrides, resynchronizes the mirror, and verifies the documented 0.5.0 package. Historical records are never rewritten.
